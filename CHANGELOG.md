## [0.7.0] - 2026-10-02

### Added

- Linux host launcher continues into Hermes automatically (ahliweb/linux-mint-xfce-rescue-ai#71): after the repair step it runs the read-only follow-up (`rescue-followup.py --mode linux-host`), writes the run report and `reports/latest-evidence.json`, then opens the portable Hermes from the USB (`hermes-portable/linux-x86_64`, `chat --cli --provider custom --model mimo-v2.6-flash -s rescue-autorun --query-file profiles/rescue-hermes/kickoff.md`, cwd `reports/`) when stdin and stdout are terminals, a key exists and the runtime is on the USB; otherwise a bilingual note and an unchanged exit code. `HERMES_HOME` is `rescue-omes/hermes-home` (profile files and `config.yaml` refreshed every run, memories and sessions kept), XDG dirs and `TMPDIR` are on the USB, `HOME` is untouched (verified with the real runtime), the key is exported only into the Hermes process from `rescue.env` parsed as data, and `RESCUE_GITHUB_ISSUES_TOKEN` is removed. New options `--no-hermes` and `--hermes-only`; numbered `[N/8]` phases with a progress bar around the collector, the analyzer and the follow-up. `tests/test_host_launchers.py` gains `LinuxHermesTests`.
- The Windows host launcher continues into Hermes after the report (ahliweb/linux-mint-xfce-rescue-ai#72), from a field run where it ended after 68 s: portable Hermes (`hermes-portable\windows-x86_64\python\python.exe -m hermes_cli.main chat --cli --provider custom --model mimo-v2.6-flash -s rescue-autorun --query-file <bundle>\profiles\rescue-hermes\kickoff.md`) in the same console with a process-scoped environment on the USB (`HERMES_HOME`, `TEMP`, `APPDATA`, `XDG_*` under `<bundle>\hermes-home`; the key only in the child environment, `RESCUE_GITHUB_ISSUES_TOKEN` removed), `hermes-home` seeded from the bundle on every run, new switches `-NoHermes` and `-HermesOnly`, and a bilingual note instead of a failure when there is no console, key, x86_64 PowerShell or runtime. It writes `reports\latest-evidence.json` and a native read-only `followup-<run_id>.json` (`windows-host`, closed vocabulary), re-scans only after an action of the run reached `execute` `ok`, writes the run report and `index.md` before Hermes starts (Hermes never changes the exit code), and shows a `[N/T]` line plus `Write-Progress` per phase, completed before Hermes opens. `tests/test_host_launchers.py` gains `WindowsHermesStaticTests` and `WindowsHermesTests`; the Hermes session itself is Hardware-required.
- Failed-unit picker in the Python repair engine (ahliweb/linux-mint-xfce-rescue-ai#81): an interactive run of `os-linux.restart-failed-units` without `--param` lists the failed services the engine reads from `systemctl --failed --no-legend --plain --type=service` itself (read-only, at most 30, valid `service_name` only) and the operator picks by number; Enter skips (`missing-param`), a number outside the list is `invalid-param`; an empty list keeps the free-text prompt; non-interactive runs and the native engines are unchanged.
- Terminal progress for every long phase (ahliweb/linux-mint-xfce-rescue-ai#67): `scripts/lib/progress.py` (`Progress`, `Budget`, `step`) and `scripts/lib/progress.sh` (`rescue_progress_step`, `rescue_progress_run`) draw only on `/dev/tty` (never stdout/stderr or the launcher log; off with `RESCUE_PROGRESS=0`, `TERM=dumb` or no terminal; `RESCUE_PROGRESS_TTY` is a test hook). `scan-target-os.py` shows five phase headers, a bar per target and the real ClamAV time budget as a bar; `opencode-go-analyze.py` shows the wait for the provider; `check-hardware-readiness.py` shows a bar over its checks. Modules get optional `Context.progress_budget`/`progress_note` hooks. Evidence, statuses, privacy rules and exit codes are unchanged; `tests/test_progress.py` covers it.
- `rescue_modules.collect_offline_target` runs the short read-only offline modules on helper threads while the ClamAV pass runs on the calling thread; results keep the fixed domain order (ahliweb/linux-mint-xfce-rescue-ai#67).
- Repair engine UX (ahliweb/linux-mint-xfce-rescue-ai#70), from a field run on a Linux host and a live USB: a root precheck (`sudo -n true` once per run; the Windows and macOS launchers check administrator rights and `euid` 0) that never prompts for or runs an action the session cannot run as root, journaling `approval unavailable needs-root` (new reason, replaces the host launchers' `not-applicable`) and marking it `(perlu root / needs root)` in the plan; batch approval of `safe` actions in `approve-each` ("Setujui semua N aksi aman (safe) sekaligus? / Approve all N safe actions at once? [Y/n]", Enter = yes, new reason `operator-approved-batch`; quarantine, `reversible`, `irreversible`, `destructive` and `--approve` actions never join) in all three engines; an `[i/N] action_id ...` header per executed action in all three engines; an operator device picker for `block_device` parameters (`hw.smart-short-selftest`, `hw.nvme-short-selftest`) in the Python engine, listing whole disks the engine reads from `lsblk` itself (rescue USB, live media and removable disks left out unless nothing else exists; model on screen only)
- `mw.clamav-update-signatures` is now `live-linux` only: stock AppArmor (`usr.bin.freshclam`) blocks a config or database on the USB even as root, so a Linux host is never offered an update that cannot work; the scan uses the newest database it finds (USB `reports/clamav`, then `/var/lib/clamav`) and stale signatures stay `warn` (`docs/malware.md`)
- `--select ACTION_ID` under `--policy auto-safe`: an action the evidence also triggers keeps origin `catalog-trigger` and runs without a prompt; one it does not trigger stays an `operator` proposal and asks; `--select` without `:os-N` for a target action selects only the targets the evidence triggers it for
- Hermes autorun (ahliweb/linux-mint-xfce-rescue-ai#69): `scripts/rescue-followup.py --evidence FILE --reports-dir DIR [--mode live-linux|linux-host] [--state-dir DIR] [--timeout SECONDS]` runs typed read-only follow-ups for the checks an analysis flagged and writes `followup-<run_id>.json` (schema `rescue-ai/v1/followup.schema.json`, 1.0, modes `live-linux`, `linux-host`, `windows-host`; numbers, booleans and closed enums only, privacy self-check, fixtures). Recipes: per-disk SMART/NVMe attributes and the LAST self-test result (`completed-ok`, `in-progress` with percent remaining, `failed`, `aborted`, `none`), journal error counts per 13 fixed categories (host journal, or a read-only mounted Linux target in the live session), malware coverage and signature age derived from the evidence and `rescue_modules.malware` (budget-exhausted versus stale versus incomplete), and `persistence.active` from `/proc/mounts` and `/proc/cmdline` (live only). Anything needing root without it is `unknown`/`needs-root`.
- Hermes profile: fixed kickoff turn `profiles/rescue-hermes/kickoff.md` (relative paths only) and the skill `rescue-autorun` (summarize, follow-up, safe catalog proposals via `rescue-repair.py --policy auto-safe --select`, self-test timing, numbered summary); `rescue-target-os` gains the field lessons (persistence, self-test timing, malware budget and `--malware-target os-N`, host-mode unknowns, journal categories) and `rescue-boot-diagnosis` points to `rescue-autorun`; `AGENTS.md` and `SOUL.md` name the two commands Hermes may run without asking.
- `config/hermes-rescue.config.yaml`: `approvals.mode: manual` and an `approvals.deny` fnmatch list (`--approve`, `--backup-ref`, `--param`, disk/partition/bootloader/crypto/filesystem-repair tools, secret and detection-list paths, recursive deletes) that blocks even under `--yolo`; validated with the local Hermes (`config check`, `tools.approval._match_user_deny_rule`). `install-hermes-rescue.sh` and `persistence-container-build.sh` link `rescue-followup`; the persistence build requires the skill `rescue-autorun`. `tests/test_followup.py`; docs: learning loop (Autorun), security model, design.
- Portable, credential-free Hermes runtime for the host launchers, so they can continue into Hermes Agent without installing anything on the host (ahliweb/linux-mint-xfce-rescue-ai#68). `scripts/build-hermes-portable.py` (stdlib only; `--platform linux-x86_64|windows-x86_64`, cross-builds refused; `--hermes-ref` defaulting to the pinned `HERMES_REF`; `--python 3.11|3.12`; `--archive`) builds a relocatable python-build-standalone CPython via `uv` with the pinned Hermes source and its hashed `uv.lock` core dependencies (Hermes refuses wheel builds, so the source tree is added with a relative `.pth`), no venv and no symlinks, bytecode compiled at build time, exFAT/Windows name and path checks, `MANIFEST.json` with `tree_sha256`, a credential-free self-check with a precise allowlist, and a smoke test. Layout `<platform>/python/` with entry `python/bin/python3 -m hermes_cli.main` (Linux) or `python\python.exe -m hermes_cli.main` (Windows). Helper modes `--scan-tree`, `--check-archive`, `--extract-archive`, `--verify-tree`. `.github/workflows/package.yml` gains `hermes-portable-linux` and `hermes-portable-windows` jobs (read-only, uv bootstrapped from a pinned hashed wheel, no new actions) and `bundle-publish` attaches both archives and their `.sha256` to the GitHub Release. `scripts/prepare-ventoy-usb.sh --hermes-portable ARCHIVE` (repeatable) requires the checksum sidecar, refuses absolute paths, `..` and symlinks, unpacks to `<usb>/rescue-omes/hermes-portable/<platform>/` and reads back `tree_sha256`; a re-run keeps an existing runtime. New `docs/hermes-portable.md`, `tests/test_hermes_portable.py` and workflow tests.
- `scripts/migrate-persistence-state.py` carries the provider key, Hermes state, field-learned skills and case history from an old persistence image into a new one with `debugfs` (no mount, no root), keeping mode/uid/gid/mtime and taking program files and bundled skills from the new image; `e2fsck -fn` and a per-file SHA-256 read-back must pass. `docs/persistence.md` gains the procedure "Upgrade USB dengan mempertahankan kunci dan state Hermes" (backup, migrate, `prepare-ventoy-usb.sh --replace-persistence`, restore host reports, read back) and `docs/security-model.md` a row. Used to upgrade the field USB from 0.5.0 to 0.6.0 (ahliweb/linux-mint-xfce-rescue-ai#65).
- Live launcher kickoff (ahliweb/linux-mint-xfce-rescue-ai#73): after the repairs `launch-hermes-rescue.sh` runs `rescue-followup.py` as root (`sudo -n`, progress bar, never blocks Hermes, offline too) and starts Hermes in the reports folder with `-s rescue-autorun` and the fixed kickoff text of `profiles/rescue-hermes/kickoff.md` as its first turn so it works on the recommendations at once (`hermes chat --tui -q`, because the TUI ignores `--query-file`; an old bundle without the kickoff falls back to the plain `hermes --tui`). Numbered `[N/10]` phases through `progress.sh`; the re-scan after repairs now needs an entry of the same run with `stage: execute` and `outcome: ok` (JSON parse, not grep). Tests in `tests/test_hermes_scripts.py` and `tests/test_evidence_readiness.py`.

### Changed

- The Linux launcher re-collects after repairs only when an action of the run reached `stage: execute` with `outcome: ok` (the journal is parsed as JSON); a failed or unavailable action no longer costs a second scan (ahliweb/linux-mint-xfce-rescue-ai#71).
- `state_dir` parameters in host mode (only `--journal`) resolve below the parent of the `repairs` directory that holds the journal (`<usb>/rescue-omes/reports`); a journal outside a `repairs` directory gives no state directory and the action is journaled `approval unavailable provider-unavailable` instead of using a relative path
- Test hook `RESCUE_REPAIR_TEST_SUDO_PROBE=1` (the root probe is skipped under `RESCUE_REPAIR_TEST_PATH` otherwise)

## [0.6.0] - 2026-10-01

Fixes from the analysis of the USB stick after the 0.5.0 physical test (OpenCode Go session header, Ventoy USB resolution, fair malware budget, honest launcher outcomes) and two new repair targets connected to the PC running the USB: Android phones and tablets (detection, ADB repairs, fastboot/Heimdall flashing with EDL/BROM guidance) and printers (USB, installed-OS spooler, opt-in local-link network). Evidence schema 1.3; the persistence image adds `adb`, `fastboot`, `heimdall-flash` and the CUPS/IPP tools and needs a rebuild.

### Added

- `--malware-target os-N` for `scripts/scan-target-os.py` and `scripts/launch-hermes-rescue.sh`: scan only one target with the whole malware budget (a deliberate second full-disk run). Other targets report `malware-scan` `unknown`, never clean; a malformed or unknown `os-N` is a usage error (exit 2) (ahliweb/linux-mint-xfce-rescue-ai#47).
- Android phone/tablet over USB as target family `android` (`and-N`), phase 1 (ahliweb/linux-mint-xfce-rescue-ai#48): `scripts/scan-android.py` (`--list-usb` prints a bilingual table of every USB device with port path, ACPI location, speed, USB version, class, brand, Android mode and `[USB RESCUE]`/`[HUB]` markers, and says which port the phone is on; `--output` writes 0600 evidence), `scripts/rescue_modules/usb_devices.py` (read-only sysfs inventory) and `scripts/rescue_modules/android.py` (read-only fixed-argv ADB checks addressed by transport id: OS version, security patch age, verified boot, bootloader lock, SELinux, storage, battery, root indicators, device-admin/accessibility/sideload counts, Play Protect, port speed). Serials, USB strings and package names never enter evidence or output; the target id is a keyed hash. Detection-only for fastboot, Qualcomm EDL, MediaTek BROM and Samsung download modes.
- Evidence schema 1.3: family `android`, `and-N` refs, top-level `usb_ports`, 17 `android-*` and 2 `usb-*` check IDs, validator rules and fixtures. Hermes skill `rescue-android`, `docs/android.md`, security-model rows for phones as untrusted USB peers.
- Run report: outcome `dependency-missing`, honesty token `host-dependency-missing` and open item `repair-engine-failed` in the schema and the Python, PowerShell and JXA generators (ahliweb/linux-mint-xfce-rescue-ai#49).
- Printers as target family `printer` (`prn-N`), phase 1, read-only (ahliweb/linux-mint-xfce-rescue-ai#57): `scripts/scan-printers.py` (`--list` bilingual table with connection, USB port, speed, brand, state, reasons, lowest marker %, queued jobs and per-problem guidance; `--network` opt-in mDNS `_ipp._tcp`/`_ipps._tcp` on the local link only; `--output` schema 1.3 evidence), `scripts/rescue_modules/printer.py` (USB class 07, `lpstat`, `ipptool` with the fixed `scripts/lib/ipp/get-printer-attributes.test`, `ipp-usb` endpoints) and installed-OS checks `printer-target-spool-stuck`, `printer-target-spooler-service`, `printer-target-cups-service` (under the `os` scope until phase 2). Queue names, URIs, IPs, serials and job names never enter evidence or output.
- Evidence schema 1.3: `printer` family, `prn-N` refs, closed `printers[]`, detection/access values, 14 `printer-*` check IDs, validator rules and fixtures. Hermes skill `rescue-printer`, `docs/printer.md`, security-model rows for printers and the LAN as untrusted peers (ahliweb/linux-mint-xfce-rescue-ai#57).
- Android repair actions (ahliweb/linux-mint-xfce-rescue-ai#48 phase 2): catalog domain `android` with `android.trim-caches` (safe), `android.enable-package-verifier` (reversible) and `android.reboot` (safe, operator-only); engine-resolved `android_device` parameter re-looked up at execution time (authorized, same `opaque_id`) with typed refusals (`device-absent`, `device-not-authorized`, `device-ambiguous`, `device-mismatch`); scope `android` and `and-N` refs in journal and run report (Python, PowerShell, JXA); the catalog validator confines `adb` to `-t {android_device}` and a closed sub-command list; `scan-android.py --count-android`/`--repair-policy` and evidence `repair_proposals`; the live launcher offers a separate phone scan, repair and run report (default no).
- Android flashing and unbrick (ahliweb/linux-mint-xfce-rescue-ai#52), operator decisions applied: operator-invoked `android.fastboot-set-active-slot` (reversible, rollback to the slot read before), `android.fastboot-reboot`, `android.fastboot-flash-partition` (allowlist boot/init_boot/vendor_boot/dtbo/vbmeta/vbmeta_system/recovery) and `android.fastboot-update-image` (never `-w`), plus EXPERIMENTAL `android.heimdall-flash-partition` (BOOT/RECOVERY/VBMETA/DTBO). New param types `fastboot_device` (`usb:<port>`), `fastboot_slot`, `firmware_file` (absolute, `O_NOFOLLOW`, regular, size-bounded, hashed and handed over as `/dev/fd/N`) and `sha256` (the only firmware value journaled); guards `bootloader-unlocked`, `image-matches-device` (zip `android-info.txt` vs `getvar product`; zips with `flash-all` or bootloader/radio/modem/persist/efs/frp/userdata images refused, nothing extracted or run) and `single-download-mode-device`; step `expect_line`; journal reasons `bootloader-locked`, `identity-mismatch`, `firmware-invalid`, `firmware-hash-mismatch`. Read-only fastboot lock/slot/fastbootd, Heimdall and EDL/BROM checks (five check IDs). Bootloader unlock is never automated; Qualcomm EDL and MediaTek BROM get detection and guidance only.
- Printer repair actions (ahliweb/linux-mint-xfce-rescue-ai#57 phase 2): catalog domain `printer` with `printer.resume-queue` and `printer.accept-jobs` (safe), `printer.cancel-stuck-jobs` (irreversible), `printer.identify` (safe, operator-only), `printer.print-test-page` and `printer.clean-print-heads` (irreversible consumables: operator-only, no trigger, not proposable by the model, always ask) and `printer.target-quarantine-spool` (reversible, installed-OS spool into the existing quarantine). New risk class `irreversible` (always asks, even under `auto-safe`; no rollback or backup) across the catalog, journal and run-report schemas and all three engines; engine-resolved `printer_ref` (queue found again at execution time, same `opaque_id`, network queues only with `--printer-network`; refusals `printer-absent`, `printer-mismatch`, `printer-ambiguous`) and `bundle_root` (closed list of shipped files); scope `printer` and a run-report `printer` domain; `rescue-malware-quarantine spool-check|spool-quarantine|spool-verify|spool-restore`; the live launcher offers a printer scan and repair after the OS scan and the Android offer (default no), with `--printer-network`; `scan-printers.py --count`/`--repair-policy`.

### Changed

- The persistence image installs `adb` and `android-sdk-platform-tools-common` (udev rules for non-root access); an existing image needs a rebuild (ahliweb/linux-mint-xfce-rescue-ai#48).
- The persistence image installs `cups`, `cups-client`, `cups-ipp-utils`, `ipp-usb` and `avahi-utils`; an existing image needs a rebuild (ahliweb/linux-mint-xfce-rescue-ai#57).
- `android.enable-package-verifier` reads its setting back in verify (`expect_line`); the persistence image installs `fastboot` and `heimdall-flash` (ahliweb/linux-mint-xfce-rescue-ai#52).
- The installed-OS `printer-target-*` checks move from scope `os` to the new scope `printer`; `--scope os` no longer includes them (ahliweb/linux-mint-xfce-rescue-ai#57).

### Fixed

- `check-hardware-readiness.py`: `usb-boot-media` now resolves the live source (Ventoy `/dev/mapper/ventoy`, dm, partition, loop) to its USB disk through sysfs (`slaves/`, `partition`, `loop/backing_file`, the `/usbN/` device path, nvme), with `lsblk` kept as fallback and cross-check. The physical test of 0.5.0 still showed `transport=unknown, source=/dev/mapper/ventoy`; the observed text now shows the resolved chain, or where resolution stopped (`? (no slaves)` and similar), so a further failure is diagnosable from the report (ahliweb/linux-mint-xfce-rescue-ai#46). Why `ventoy_version` stays `null` in live-session evidence is documented in `docs/hardware.md`.
- Malware scan budget is shared fairly across targets: each gets `min(per-target cap, remaining / targets still to scan)` and unused time carries forward, in default and `--malware-full-disk` mode. In the 0.5.0 physical test the first target (Windows) used the whole 3300 s full-disk budget and the second (Linux Mint) was never scanned (ahliweb/linux-mint-xfce-rescue-ai#47).
- OpenCode Go analysis never ran in the 0.5.0 physical test: the gateway refuses every request without `x-opencode-session` (HTTP 400 `MissingSessionID`). The analyzer and the PowerShell and macOS engines now send `ses_` plus the first 32 hex characters of the sha256 of the evidence JSON they send (a hash, never evidence content). This is the patch the field session applied and verified, upstreamed (ahliweb/linux-mint-xfce-rescue-ai#45).
- A provider HTTP 4xx answer (other than 401/403/408/429) is no longer labelled `network-error`: the analyzer exits `5` and the run outcome is the new `provider-rejected` (run report schema, Python/PowerShell/JXA generators, honesty token `provider-rejected-request`). The bilingual message shows the HTTP status and the provider error type only when it is a short token, never the response body; launcher exit codes are unchanged (ahliweb/linux-mint-xfce-rescue-ai#45).
- Linux host launcher: a repair-engine failure no longer overwrites the analyzer or scan outcome. The first failure stays the run outcome and exit code; the engine failure is added as the open item `repair-engine-failed` (`exit-2`/`exit-3`) through the new `rescue-report.py --repair-exit`. An unusable repair journal still outranks (`journal-unusable`, exit 5). On the USB, two 0.5.0 field runs on a Linux Mint 21.3 host showed only `repair-invalid` and hid the real cause (ahliweb/linux-mint-xfce-rescue-ai#49).
- Linux host launcher: without python3-jsonschema on the host it prints a bilingual note, installs nothing, skips the analyzer, the repair engine and the network, keeps the evidence and ends with outcome `dependency-missing` (exit 6) instead of a confusing `analysis-failed`/`repair-invalid` — the probable cause of those field runs (#49).
- Linux host launcher: stdout and stderr of the launcher and its tools are logged to `reports/launcher-linux-<utc>.log` on the USB (0600 where the filesystem has modes; never holds the key); evidence and report share one run id (the post-repair evidence uses `<run id>-after`); the report header catalog SHA-256 is computed from the bundle catalog when no journal exists (#49).
- Windows, macOS and live launchers keep the first failure outcome when the repair engine exits 2: `repair-invalid` only replaces `completed`/`evidence-only`/`dry-run`, an unusable journal still outranks. The PowerShell and JXA generators emit the open item `repair-engine-failed` (`exit-2`/`exit-3`) exactly like `rescue-report.py --repair-exit`, which the live launcher now passes (ahliweb/linux-mint-xfce-rescue-ai#56).

Credential-free packages on GitHub Packages, built only in CI. v0.5.0 was the first to be published (via `workflow_dispatch`) and was verified anonymously: checksums match and no key is present. The runtime behavior is unchanged from 0.5.0.

### Added

## [0.5.0] - 2026-10-01

Fixes from the first physical boot on a Windows laptop. The live preflight no longer stops the run: under Ventoy the USB is detected through `/dev/mapper/ventoy`, and without Wi-Fi the local read-only scan, catalog repairs and report still run. The terminal never closes silently. New guide for the Secure Boot first boot.

### Added

- `docs/secure-boot.md`: operator guide (Bahasa Indonesia) for the Secure Boot error on the first boot of the USB on a new machine. Covers the one-time Ventoy MOK enrollment (`ENROLL_THIS_KEY_IN_MOKMANAGER.cer` on `VTOYEFI`), firmware options to check when MokManager is not offered, a BitLocker recovery-key warning, and recording the state with `mokutil --sb-state`. The physical steps are Hardware-required. ahliweb/linux-mint-xfce-rescue-ai#38

### Fixed

- Live boot no longer stops silently (ahliweb/linux-mint-xfce-rescue-ai#37, found on a physical boot under Ventoy). `scripts/check-hardware-readiness.py` resolves the live-media source through dm devices (`/dev/mapper/ventoy`), partitions, and loop devices (`backing_file` plus `findmnt -T`, bounded depth) to the physical disk and uses its transport and size; `usb-boot-media` is `pass` for a large enough USB disk, `fail` only for a resolved USB disk below the minimum, and `warn` when the source cannot be resolved or is not USB. `internet-connectivity` is no longer required and is `warn` (overall `ready_with_warnings`) when offline. The launcher waits up to about 60 s for a default route, offers a bilingual connect-or-continue-offline prompt on a terminal (`L`, EOF, or 180 s continues offline), and offline runs the local scan, the catalog repairs, and the run report without the OpenCode Go analysis (`network-error`) and without Hermes. Any non-zero exit on a terminal prints a bilingual summary and waits for Enter; stdout/stderr are also kept in a local `0600` `<state-dir>/reports/launcher-<utc>.log`. The autostart entry now opens `xfce4-terminal --maximize -x` explicitly (`Terminal=false`), and the same entry is installed into `~/.local/share/applications/` to re-run from the menu.
